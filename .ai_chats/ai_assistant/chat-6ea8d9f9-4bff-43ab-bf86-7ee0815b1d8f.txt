You can use Kotlin's `zipWithNext` combined with the standard idiom of keeping only the first item of each "run" of equal statuses. The cleanest functional way is to use a helper that collapses consecutive duplicates by a key — Kotlin doesn't have a built-in `distinctUntilChangedBy` for `List`, but you can express it with `fold`, or even more simply by filtering with an index lookup.

Here are two equivalent functional options:

### Option 1: `fold` (most idiomatic)

<llm-snippet-file>KeepMapper.kt</llm-snippet-file>
```kotlin
// ... existing code ...
                val proposalStageHistory = proposalCommits.second
                    .map { proposalCommit ->
                        StageHistory(
                            projectId,
                            proposalId,
                            proposalCommit.index,
                            proposalCommit.proposalData.status,
                            proposalCommit.commitedAt,
                        )
                    }
                    .fold(emptyList<StageHistory>()) { acc, sh ->
                        if (acc.lastOrNull()?.status == sh.status) acc else acc + sh
                    }

                return emptyList()
// ... existing code ...
```

### Option 2: filter by previous element via `zipWithNext`

```kotlin
val stages = proposalCommits.second.map { /* StageHistory(...) as above */ }
val collapsed = stages.take(1) + stages.zipWithNext()
    .filter { (prev, curr) -> prev.status != curr.status }
    .map { it.second }
```

### Option 3: extract a reusable extension

If you find yourself doing this in multiple places (e.g. also for KEP), define it once:

```kotlin
inline fun <T, K> List<T>.distinctUntilChangedBy(selector: (T) -> K): List<T> =
    fold(mutableListOf()) { acc, item ->
        if (acc.isEmpty() || selector(acc.last()) != selector(item)) acc.add(item)
        acc
    }
```

Then the call site becomes:

```kotlin
val proposalStageHistory = proposalCommits.second
    .map { pc ->
        StageHistory(projectId, proposalId, pc.index, pc.proposalData.status, pc.commitedAt)
    }
    .distinctUntilChangedBy { it.status }
```

### How it behaves on your "back and forth" case
Given statuses (in commit order): `Submitted, Submitted, Accepted, Submitted, Submitted, Rejected`

The result keeps:
- `Submitted` (first occurrence, with its `createdAt`)
- `Accepted` (status changed)
- `Submitted` (status changed back — kept again, since it's not in succession with the previous `Submitted`)
- `Rejected` (status changed)

That matches your requirement: only the *first* entry of each run of identical statuses is kept, but a status that returns later starts a new run and is kept again.

### A small note on `stageIndex`
After collapsing, `stageIndex` will no longer be a contiguous `0,1,2,…` because it inherits the original commit index. If you'd like it to be a dense sequence over the kept stage transitions, re-index after collapsing:

```kotlin
.distinctUntilChangedBy { it.status }
.mapIndexed { i, sh -> sh.copy(stageIndex = i) }
```

Pick whichever semantics you prefer for `stageIndex` — keep the original commit index (traceable back to the revision) or re-index per stage transition (dense, matches its name better).

/**
 * Reads a JSONL file (`<dir>/<stream>.jsonl`) and returns each line as a
 * [JsonObject]. Lines that aren't objects (or fail to parse) are skipped.
 * Returns an empty sequence if the file does not exist.
 */
fun readJsonlObjects(dir: Path, stream: String): Sequence<JsonObject> {
    val path = dir.resolve("$stream.jsonl")
    if (!Files.exists(path)) return emptySequence()
    return sequence {
        Files.newBufferedReader(path).use { reader ->

package dev.cse3000.loader

import kotlinx.serialization.json.Json
import kotlinx.serialization.json.JsonElement
import kotlinx.serialization.json.JsonObject
import java.nio.file.Files
import java.nio.file.Path

private val json = Json { ignoreUnknownKeys = true }

/**
 * Reads a JSONL file (`<dir>/<stream>.jsonl`) and returns each line as a
 * [JsonObject]. Lines that aren't objects (or fail to parse) are skipped.
 * Returns an empty sequence if the file does not exist.
 */
fun readJsonlObjects(dir: Path, stream: String): Sequence<JsonObject> {
    val path = dir.resolve("$stream.jsonl")
    if (!Files.exists(path)) return emptySequence()
    return sequence {
        Files.newBufferedReader(path).use { reader ->
            for (line in reader.lines()) {
                if (line.isBlank()) continue
                val element: JsonElement = runCatching { json.parseToJsonElement(line) }.getOrNull() ?: continue
                if (element is JsonObject) yield(element)
            }
        }
    }
}

Use `groupingBy { id }.reduce { … }` to keep, per id, the entry with the maximum `_scraped_at`. Since your timestamps are ISO-8601, lexicographic string comparison gives the correct ordering, so no parsing is needed.

```kotlin
val issueComments = readJsonlObjects(normalizedDir, "keep-issue-comments")
    .groupingBy { it.getJsonString("id") }
    .reduce { _, acc, obj ->
        if (obj.getJsonString("_scraped_at") > acc.getJsonString("_scraped_at")) obj else acc
    }
    .values
    .toList()
```

### Notes

- **`groupingBy { … }.reduce { … }`** processes the sequence lazily/iteratively and keeps just one accumulator per key — much more memory-efficient than `groupBy { … }.mapValues { it.value.maxBy(...) }`, which would materialize all groups.
- If `id` is a JSON number rather than a string, swap `getJsonString("id")` for something like `it["id"]!!.jsonPrimitive.content` (works for both), or `.int` if you specifically want it typed.
- If you'd rather group later (e.g. by `_issue` as you already do), do the dedup *first*, then group:

```kotlin
val issueComments = readJsonlObjects(normalizedDir, "keep-issue-comments")
    .groupingBy { it.getJsonString("id") }
    .reduce { _, acc, obj ->
        if (obj.getJsonString("_scraped_at") > acc.getJsonString("_scraped_at")) obj else acc
    }
    .values
    .groupBy { it.getJsonString("_issue") }
```

                val rootCreatedAt = issue.getJsonString("created_at")
                val rootLogin = issue["user"]!!.jsonObject.getJsonString("login")
                val rootAuthorId = resolveGHLogin(rootLogin)

                if (issueNumber in prIssueCommentIssueNumber)
                    log.error("proposal id $issueNumber exists in keep-pr-issuecomments")

                val rootComment = Comment(
                    commentIds.nextId(),
                    rootAuthorId,
                    projectId,
                    proposalId,
                    null,
                    rootCreatedAt,
                    rootContent,
                )

                val issueComments = issueToIssueComments[issueNumber] ?: emptyList()

                val commentIdBuffer = listOf(rootComment.commentId) + (0..issueComments.size).map { commentIds.nextId() }

                val comments = issueComments.sortedBy { it.getJsonString("created_at") }

                            commentIdBuffer[index + 1],
                            authorId,
                            projectId,
                            proposalId,
                            commentIdBuffer[index],
                            createdAt,
                            content,
                        )
                    }

                listOf(rootComment) + comments
            }.toList()
    }

package dev.cse3000.loader

import java.util.concurrent.atomic.AtomicLong

/**
 * Allocates sequential IDs in the half-open range `[base, base + capacity)`.
 *
 * Convention for this loader: `base = smallestAssignedProjectId * 1_000_000L`,
 * `capacity = 1_000_000L`. With 10 projects total, ranges never overlap, so
 * Person/Organisation/Comment IDs allocated by different contributors never
 * collide.
 */
class IdAllocator(private val base: Long, private val capacity: Long = 1_000_000L) {
    private val next = AtomicLong(base)

    fun nextId(): Long {
        val id = next.getAndIncrement()
        check(id < base + capacity) {
            "IdAllocator exhausted: base=$base capacity=$capacity. Bump capacity in IdAllocator construction."
        }
        return id
    }
}

Assistant: 
Yes — the `commentIdBuffer` indexing trick works but is fragile (the `0..size` is off-by-one — it should be `0 until size` — and you have to mentally track `index` vs `index + 1`). The idiomatic functional pattern for "map while threading the previous result" is `runningFold` (a.k.a. `scan`). It's exactly designed for this.

Here's the rewrite:

```kotlin
val sortedComments = issueComments.sortedBy { it.getJsonString("created_at") }

val comments = sortedComments
    .runningFold(rootComment) { previous, commentJson ->
        val login = commentJson["user"]!!.jsonObject.getJsonString("login")
        Comment(
            commentId = commentIds.nextId(),
            authorId = resolveGHLogin(login),
            projectId = projectId,
            proposalId = proposalId,
            commentOnCommentId = previous.commentId,
            createdAt = commentJson.getJsonString("created_at"),
            content = commentJson.getJsonString("body"),
        )
    }

comments  // already includes rootComment as the first element
```

### Why this is better

- **`runningFold(initial) { acc, item -> … }`** returns `[initial, f(initial, item0), f(f(initial,item0), item1), …]` — i.e. each step has access to the previously produced element, and the seed is included in the result. That maps 1:1 onto your "each comment links to the previous comment's id" requirement.
- No id buffer, no off-by-one, no separate `listOf(rootComment) + comments` concatenation.
- The lambda is a pure function of `(previous, currentJson)`, which is easier to read and test.

### A subtle bug you may want to fix while you're there

In your current code the author of every reply is computed from `issue["user"]` (the issue opener), not from `comment["user"]`. The rewrite above uses `commentJson["user"]` — double-check whether that's what you want; if you really do want the issue opener as author, swap it back.

### Side note: `commentIds` ordering

`runningFold` evaluates the lambda left-to-right, so `commentIds.nextId()` is called in chronological order of the comments — same as before. If at some later point you switch to a parallel/unordered pipeline, you'd need to allocate ids up front, but for a plain `List` this is fine.

It looks like you're asking about the snippet — there are two issues with it:

1. **Type mismatch in the `when` branches.** The `superseded` and `else` branches return `Pair<String, String?>`, but the middle branch returns `List<String>` (from `split`). The compiler will infer the common supertype `Any`, and destructuring `(status, implementedAt)` won't work the way you want.
2. **`rawStatus.contains("in")` is too permissive** — it matches any status containing the letters `in`, e.g. `Stable**in** 1.9` ✅ but also a hypothetical `Pending` ❌. Splitting on the substring `"in"` would also break those.

A cleaner version using a real word boundary (whitespace around `in`) and consistent `Pair` types:

```kotlin
val (status, implementedAt) = when {
    rawStatus.equals("superseded", ignoreCase = true) -> rawStatus to null
    " in " in rawStatus -> {
        val (s, v) = rawStatus.split(" in ", limit = 2)
        s.trim() to v.trim()
    }
    else -> rawStatus to null
}
```

### Even nicer: a single regex

If you want one expression that handles all three cases uniformly:

```kotlin
private val statusRegex = Regex("""^(?<status>\S+(?:\s+\S+)*?)(?:\s+in\s+(?<version>.+))?$""")

val match = statusRegex.matchEntire(rawStatus.trim())
    ?: error("Unrecognized status: $rawStatus")
val status = match.groups["status"]!!.value
val implementedAt = match.groups["version"]?.value
```

This naturally allows multi-word statuses like `superseded` or `Partially Stable` without a special case, and only treats `in` as a separator when surrounded by whitespace.

### Minor nitpick

`rawStatus.contains("superseded")` is case-sensitive; if your input might be `Superseded`, use `contains("superseded", ignoreCase = true)` or normalize once at the top:

```kotlin
val rawStatus = metaMap["status"]!!.trim()
```

Pick the variant that fits your data — the first version is the smallest change to your existing code; the regex version scales better if more status formats appear later.
