     Rename-aware revision walk for the proposal revision scraper

     Context

     The proposal revision scraper in scraper/ powers KEEP and KEP data
     ingestion. Its RevisionWalker
     (scraper/src/main/kotlin/dev/cse3000/gh/git/RevisionWalker.kt) walks
     per-file commit history via JGit and emits one JSONL row per (path,
     commit). It has an explicit, documented limitation
     (RevisionWalker.kt:28-31): it does not follow file renames — a renamed
     proposal loses its pre-rename history, and downstream mappers
     (KeepMapper.kt, KepMapper.kt) treat the old and new path as two unrelated
     proposals.

     This is a real, non-rare problem in both projects:

     - KEEP mass-renamed its proposal files at multiple points in its history.
     Without rename-following, large swaths of revision history are missing or
     split into phantom proposals.
     - KEP restructured every proposal from a single keps/<sig>/<date>-<slug>.md
      file into a keps/<sig>/<NNNN>-<slug>/{kep.yaml,README.md} directory. The
     single-file .md was renamed (via git mv) into the directory's README.md.
     The current KepMapper compensates with ad-hoc slug-matching
     (KepMapper.kt:202-247, plus a separate kep-revisions-other stream); JGit's
     rename detector should handle this natively, so that scaffolding can go
     away.

     Verdict: yes, JGit's FollowFilter + RenameCallback give us git log --follow
      behavior in-process. This plan implements rename-following in the walker,
     unifies the mapper-side grouping into shared logic, removes KepMapper's
     pre-migration stitching, and bakes in a one-shot cursor wipe + full refill
     as part of the rollout.

     Design

     Walker: per-path FollowFilter with RenameCallback

     Replace the inner walkPath loop in RevisionWalker.kt:105-125 (currently
     git.log().add(headId).addPath(path).not(sinceId)) with a manual RevWalk
     driving FollowFilter. The outer loop over HEAD paths
     (RevisionWalker.kt:45-85, listPathsAtHead at :87-103) stays as-is.

     Why this and not a full-history pass with
     DiffFormatter.setDetectRenames(true):
     - Matches the existing per-path structure with minimal disruption.
     - FollowFilter invokes rename detection only when the followed path
     disappears between parent and commit, so the common no-rename case costs
     the same as today.
     - KEEP ~150 paths + KEP ~700 dirs = a few thousand per-path walks.
     Performance stays inside today's envelope.

     Mappers: shared grouping by head_path

     Both mappers currently group revisions by the per-commit path field. After
     rename-following, the right grouping key is the stable HEAD path
     (head_path) — the same logical proposal's revisions appear under that
     single key even when their historical filename changes.

     The grouping pipeline (dedup → sort → group) is identical between mappers;
     only the key derivation differs (KEEP groups by head_path, KEP groups by
     head_dir). Factor that pipeline into a new shared utility in loader/.

     KEP simplification: drop the slug-stitching

     Once the walker emits pre-migration history under the modern head_dir, the
     oldFormatByPath stream (KepMapper.kt:202-247) and the kep-revisions-other
     stream produced by KepRevisionCollector.kt become dead weight — the same
     revisions arrive natively through kep-revisions-readme walks that cross the
      git mv. Remove both.

     Key JGit pieces

     - org.eclipse.jgit.revwalk.FollowFilter.create(path, 
     repo.config.get(DiffConfig.KEY)) — the TreeFilter that tracks a single path
      across renames.
     - org.eclipse.jgit.diff.RenameCallback — fires before the renamed commit is
      yielded; mutate a currentPath variable in its renamed(DiffEntry) override
     using diff.oldPath.
     - RevWalk.markStart(head) + RevWalk.markUninteresting(sinceId) — replaces
     LogCommand.add().not(). LogCommand cannot accept a custom TreeFilter, which
      is why we drop it here.
     - Default rename score (60%) and rename limit (1000) are the JGit defaults.
      Watch KEEP/KEP rename quality during the first re-scrape; if a known
     rename is missed because the body was also heavily rewritten, lower the
     score on the DiffConfig (config.setInt("diff", null, "renameLimit", ...))
     before constructing the FollowFilter.

     Implementation

     1. scraper/src/main/kotlin/dev/cse3000/gh/git/RevisionWalker.kt

     - Open RevWalk(repo).use { rw -> ... }; markStart(rw.parseCommit(headId));
     if sinceId != null, markUninteresting(rw.parseCommit(sinceId)).
     - Construct FollowFilter.create(path, repo.config.get(DiffConfig.KEY)).
     Register a RenameCallback that captures diff.oldPath into a local var 
     currentPath = path.
     - Set rw.treeFilter = followFilter.
     - Iterate for (commit in rw) { ... }. After each iteration currentPath
     reflects the path at that commit (the callback fires before the commit is
     yielded when crossing a rename). Read the blob via existing
     blobContent(repo, commit, currentPath).
     - Wrap iteration in runCatching like the current :115.

     Extend buildRow (:136-154) with new fields:
     - head_path — the stable HEAD-path key (constant across the walk for one
     outer iteration). Used for grouping downstream.
     - head_dir — derived from head_path analogously to existing dir (:141).
     - Keep path and dir: their semantics are now "path/dir at this commit",
     which matches what they'd have been if rename-following had existed from
     day one.
     - Optional renamed_from for rename-event commits (set when the callback
     fired during that commit).

     Update the class doc comment at :20-31 to describe the new behavior and

     No changes needed to walk() (:45-85), listPathsAtHead (:87-103), headSha()

     2. KEP collector: collapse streams

     In kep/src/main/kotlin/dev/cse3000/kep/KepRevisionCollector.kt:18-25, drop
     the per-path stream split. Emit every row to a single stream
     kep-proposal-revisions (mirroring KEEP). The mapper decides
     yaml-vs-readme-vs-old-format per-commit from the row's path field. This
     removes the kep-revisions-yaml / kep-revisions-readme / kep-revisions-other
      distinction at the writer level and makes the shared grouping utility
     trivially applicable.

     3. New shared utility: 
     loader/src/main/kotlin/dev/cse3000/loader/RevisionGrouping.kt

     A small object RevisionGrouping exposing:

     - readGroupedByHeadPath(normalizedDir: Path, stream: String): Map<String, 
     List<JsonObject>>

       - Dedups via existing keepLatestScrapesBy { headPathOf(it) + ":" + 
     it.getJsonString("commit_sha") }.
       - Sorts by committed_at.
       - Groups by headPathOf(it).

     Incremental CommitsCollector

     Context

     scraper/.../gh/scraper/CommitsCollector.kt fetches commits via GitHub's
     REST /repos/{slug}/commits endpoint to capture author.login — the
     GitHub-resolved identity attached to each git commit. It's consumed by
     CommonMapper.loginsToGitAuthors (loader/.../CommonMapper.kt:260-296), which
      builds a per-login set of git names and emails for person enrichment. That
      mapping is the only thing the downstream pipeline needs from this stream.

     The collector currently fetches the full set every run. The class docstring
      (CommitsCollector.kt:22-25) still describes an incremental mode that
     tracks commit.committer.date and passes ?since= — but commit 1da602d
     ("don't use cursor for GitHub commits, commit timestamps are not to be
     trusted") removed it. The reason was exactly what this question raises:
     committer dates can move backwards on a branch (back-merges, rebases of a
     feature branch onto an older base) and force pushes invalidate any
     monotonic watermark. A pure ?since= cursor silently drops the late-arriving
      older commits.

     We want incremental behavior without ever missing a commit, including in
     the two failure modes:
     1. Out-of-order commits — new commits with committer dates older than the
     cursor (back-merges, branch reparenting).
     2. Force pushes — branch tip rewritten; some previously-emitted SHAs are
     now unreachable from any ref, new SHAs take their place.

     Verdict

     Yes, this is possible. The key move is to stop using commit timestamps as 
     the source of truth and instead drive enumeration from the local git mirror
      (already kept current by RepoMirror.ensureUpToDate()'s default refspec
     +refs/heads/*:refs/remotes/origin/*, which accepts non-fast-forward
     updates) plus a persisted SHA set. git fetch reliably surfaces every commit
      reachable from current refs regardless of date order or rewrites — that's
     the property we need.

     Design

     Source of truth: local mirror, not the API

     After RepoMirror.ensureUpToDate(), every commit currently reachable on any
     tracked branch is in the local bare clone. JGit can enumerate them
     deterministically. This is the same mechanism RevisionWalker
     (scraper/.../gh/git/RevisionWalker.kt) already uses for per-path revision
     walks, and it's the property we leverage here.

     Per-commit GitHub fetch for new SHAs

     author.login resolution requires GitHub's view of the commit (it isn't in
     the git data). So for each new commit, call /repos/{slug}/commits/{sha}
     individually. This endpoint returns the same shape as the bulk list, so the
      downstream consumer is unaffected.

     Persisted state: a SHA set

     Add a per-repo set of already-emitted commit SHAs to ScrapeContext. Re-use
     the existing data/cache/-rooted state pattern (SyncCursor at
     scraper/.../gh/cache/SyncCursor.kt is the template for a single key→value
     map; this needs key→Set of strings — a small new state class alongside it).
      On each run:

     1. RepoMirror.ensureUpToDate() — already wired.
     2. Enumerate all commit SHAs reachable from refs in the local mirror via
     RevWalk (no tree filter needed — every commit, not per path; see rationale
     below).
     3. newSHAs = enumeratedSHAs − persistedSet.
     4. For each SHA in newSHAs (with bounded concurrency, like the rest of the
     client), GET /repos/{slug}/commits/{sha}, emit the row, add to set.
     5. Persist set.

     Drop per-path filtering

     Today CommitsCollector runs one paginated query per path
     (KeepCommitsCollector.kt:21-23 discovers ~150 paths). After the redesign,
     fetching is by SHA, not by path — there's no API-side filtering to take
     advantage of. Walking the local mirror once (every commit) is simpler and
     strictly more complete: a commit that touches multiple proposal paths
     becomes one SHA, one API call, one row. Downstream dedup keyed on sha
     (KEEP/KEP mappers do keepLatestScrapesBy { "_path:sha" } today; would
     become just sha) is unaffected — loginsToGitAuthors is set-based, so over-
     or under-inclusion of unrelated commits only widens or narrows the
     login→authors map but doesn't break it.

     Optionally, keep a path filter applied post-fetch (skip emitting commits
     whose tree diff doesn't touch matching paths) if we want to preserve the
     current scope. Since the mapper just needs (login, name, email) triples and
      is order-independent, I'd drop the filter — fewer special cases, more
     comprehensive identity data.

     Force-push handling

     Three relevant properties of git fetch with
     +refs/heads/*:refs/remotes/origin/*:
     - Non-fast-forward updates are accepted (+ prefix).
     - Old commits orphaned by the rewrite are not automatically deleted — they
     remain in the object database until GC runs (and JGit's default doesn't
     aggressively GC unreachable objects).
     - A bare mirror cloned with setCloneAllBranches(false) (current code in
     RepoMirror.kt:43) tracks only the default branch. Force-pushing to it makes
      old reachable SHAs unreachable.

     Two reasonable policies for the SHA set:

     A. Append-only (recommended). Once an SHA is in the set, it stays. Orphaned
      SHAs remain in the historical JSONL (and downstream dedup keeps the latest
      scrape). The login→authors map already has whatever they contributed. No
     re-fetch, no lost data. The set grows monotonically; for KEEP/KEP, that's
     bounded (~5k for KEEP, ~15k for KEP) and trivially fits in a JSON file.

     B. Reconcile to reachable set. On each run, intersect the persisted set
     with reachable SHAs and discard orphans. This is closer to "current state
     of the repo" but causes the historical JSONL and the cache to drift — the
     rows are still there but the SHA cache no longer says they were fetched.
     Loses the audit trail.

     Recommended: A. Document the orphan-retention semantics; mappers don't
     care.

     Back-merge handling (out-of-order commits)

     After git fetch, every reachable commit is in the local repo regardless of
     committer date. The SHA-set diff at step 3 catches back-merged old commits
     the same way it catches new tip commits — there's no timestamp comparison
     anywhere in the flow.

     Implementation

     Critical files

     - scraper/src/main/kotlin/dev/cse3000/gh/scraper/CommitsCollector.kt —
     rewrite. Replace the API-paginated bulk fetch with: local-RevWalk
     enumeration → SHA-set diff → per-new-SHA single-commit fetch.
     - scraper/src/main/kotlin/dev/cse3000/gh/cache/SeenShas.kt — new file. A
     Map<repoSlug, Set<sha>> state class, modeled on SyncCursor.kt
     (mutex-guarded, atomic-rename persist via temp file). Persisted at
     data/cache/seen-commit-shas.json.
     - scraper/src/main/kotlin/dev/cse3000/gh/io/ScrapeContext.kt:11-44 — add
     seenShas: SeenShas field; instantiate in create() (:33-42) alongside
     cursor/gitCursor; call seenShas.persist() in persist() (:21-25).
     - keep/src/main/kotlin/dev/cse3000/keep/KeepCommitsCollector.kt and
     kep/src/main/kotlin/dev/cse3000/kep/KepCommitsCollector.kt — pass a
     RepoMirror (or use the same one the revision collector already opens) into
     CommitsCollector. Drop the per-path discovery — it's no longer needed.
     - scraper/src/main/kotlin/dev/cse3000/gh/scraper/GenericScraper.kt:60-68 —
     same constructor change, no longer carries pathFilter.
     - loader/src/main/kotlin/dev/cse3000/loader/KeepMapper.kt:75-82 and

     "_path:sha" to just sha. Behavior is unchanged for commits with a single

     Collector flow (replaces CommitsCollector.run + collectStream)

     constructor(client, sink, mirror, repoTag, seenShas)
     run():
         mirror.ensureUpToDate()
         val reachable = enumerateReachableShas(mirror.repository)   // RevWalk,
      all refs
         val seen = seenShas.get(slug)
         val toFetch = reachable - seen
         log "incremental commits: reachable=R seen=S new=N"
         fetch each sha in toFetch (bounded concurrency, reuse client.getJson):
             sink.emit("$repoTag-commits", obj, {"repo": slug})
             seenShas.add(slug, sha)
         persist deferred to ScrapeContext.persist()

     enumerateReachableShas: same pattern as RevisionWalker.listPathsAtHead
     (RevisionWalker.kt:94-110) — RevWalk(repo), markStart from each ref tip in
     repo.refDatabase.refs, iterate, collect commit.id.name. No setTreeFilter
     (we want every commit).

     Bootstrap

     First run on an existing data directory will see an empty seenShas set and
     N reachable commits. The collector will issue N individual API calls. For
     KEEP (~3-5k commits on proposal paths in the current per-path scope, ~25k
     commits total in the repo) this is a one-shot operation taking maybe an
     hour on a single-token rate limit (5000/hour). To avoid this:

     - Either accept the one-time cost (it's bounded and the loader can keep
     running with the existing stale JSONL until the bootstrap completes).
     - Or run a parallel bootstrap step that ingests the existing
     *-commits.jsonl and seeds seenShas from the SHA field of every row. This
     makes the first incremental run after deploy emit zero new commits if no
     new ones landed since the last bulk scrape. Simple Gradle one-shot or a CLI
      flag; ~50 lines.

     Recommend the seed approach — it makes the transition seamless. The seed
     can be a seedFromJsonl method on SeenShas that reads
     data/normalized/{keep,kep}-commits.jsonl, extracts sha, adds to the set,
     persists.

     Cost trade-off

     ┌─────────────────┬───────────────────────────┬──────────────────────────┐
     │                 │           Today           │ Proposed (steady state)  │
     ├─────────────────┼───────────────────────────┼──────────────────────────┤
     │ KEEP per run    │ ~150 paginated calls      │ ~5–20 individual calls   │
     │                 │ (paths)                   │ (new SHAs)               │
     ├─────────────────┼───────────────────────────┼──────────────────────────┤
     │ KEP per run     │ similar magnitude         │ similar magnitude        │
     ├─────────────────┼───────────────────────────┼──────────────────────────┤
     │ Bootstrap       │ n/a                       │ ~N individual calls (or  │
     │                 │                           │ 0 via seed)              │

     ├─────────────────┼───────────────────────────┼──────────────────────────┤
     │ Misses on force │ depends on since=         │ none                     │
     │  push           │ interplay                 │                          │
     └─────────────────┴───────────────────────────┴──────────────────────────┘

     per run for typical incremental scrapes.

  Root cause: Truncated response from api.github.com. This isn't rare under high concurrency against shared CDNs — connections drop, proxies time
  out, HTTP/2 streams get RST. Ktor's CIO engine surfaces this as IllegalStateException("Content-Length mismatch: …") from checkContentLength,
  fired when resp.bodyAsText() runs the saved-body integrity check.

  Why your retry logic doesn't trigger: GithubClient.fetchWithRetry at GithubClient.kt:181 only retries java.io.IOException. IllegalStateException
   out, HTTP/2 streams get RST. Ktor's CIO engine surfaces this as IllegalStateException("Content-Length mismatch: …") from checkContentLength,
  fired when resp.bodyAsText() runs the saved-body integrity check.

  Why your retry logic doesn't trigger: GithubClient.fetchWithRetry at GithubClient.kt:181 only retries java.io.IOException.
  IllegalStateException is not an IOException, so it falls right through the catch list straight back up. The retry loop never gets to back off.
  Why your runCatching guards don't save you: They should — the exception is thrown from resp.bodyAsText() inside fetchWithRetry, propagates out

  hierarchy. Under flatMapMerge, one failed sub-flow cancels its siblings and the merged flow rethrows.

  Recommended fix (one-line): extend fetchWithRetry's catch list to treat content-length mismatches as retryable transient errors, alongside
  IOException. Something like:

  } catch (e: IllegalStateException) {
      // Ktor's CIO surfaces truncated/dropped responses ("Content-Length mismatch"
      // and similar low-level connection failures) as IllegalStateException — same
      // operational shape as IOException, retry the same way.
      if (attempt > maxRetries) throw e

      delay(backoff)
      attempt++
