     Plan: GitHub scraper for Kotlin/KEEP and kubernetes/enhancements

     Context

     This is a TU Delft CSE3000 research project (RQ3) doing a comparative study
      of two
     ecosystem proposal processes:

     - KEEP — Kotlin Evolution and Enhancement Process. Hosted at Kotlin/KEEP.
     Proposals are markdown files merged via PR, but discussion happens 
     primarily
     on the repo's GitHub Discussions tab (GraphQL-only API).
     - KEP — Kubernetes Enhancement Proposals. Hosted at
     kubernetes/enhancements.
     Each proposal is a directory under keps/ containing a kep.yaml, README, and
     PRR docs, with a tracking issue and discussion spread across multiple PRs 
     and
     issues (REST works fine).

     The goal of this scraper is to download everything that might be needed for
     both repos in one pass, persist it locally for offline processing, and
     support
     incremental refresh via a Gradle task without re-downloading what hasn't
     changed (since the GitHub API rate limit is a concern). The final analysis
     target is a MySQL database with a schema TBD, so the scraper output should
     be structured but loosely-coupled to any specific schema (JSON-on-disk is
     the
     right level of abstraction). The :rq3 analysis module is out of scope here.

     The project is currently a clean Gradle multi-module scaffold (Kotlin
     2.3.20, JVM
     toolchain 25). All src/main/kotlin directories are empty. Existing version
     catalog already provides kotlinx-coroutines 1.10.2,
     kotlinx-serialization-json
     1.9.0, and kotlinx-datetime 0.7.1.

     Approach

     Hybrid HTTP layer — Ktor Client for REST + a hand-written GraphQL escape
     hatch in the same Ktor stack. No Apollo, no second HTTP framework. Reasons:

     - For ~500 proposals total, REST + ETags is simpler, gives self-documenting
     JSON-on-disk artifacts (good for a thesis appendix), and supports cheap
     incremental reruns via If-None-Match.
     - KEEP's GitHub Discussions tab forces some GraphQL. We add a single
     runGraphQL(query, variables) method to the Ktor client and write the few
     queries we need by hand (repository.discussions, discussion.comments,
     discussion.comments.replies, reactions). Apollo's codegen + schema tooling
     is overkill for ~3-4 queries.
     - KEP's discussions are issue/PR comments → pure REST.

     Two-tier disk persistence under data/ (gitignored):

     data/
       cache/
         raw/<repo>/<endpoint>/<id>.json     # verbatim API responses
         etags.json                          # url -> etag
         last-sync.json                      # endpoint -> max(updated_at)
       normalized/
         keep-proposals.jsonl, keep-comments.jsonl, keep-reviews.jsonl,
         keep-discussions.jsonl, keep-discussion-comments.jsonl,
         kep-proposals.jsonl, kep-comments.jsonl, kep-reviews.jsonl,
         kep-yaml.jsonl, users.jsonl, reactions.jsonl, labels.jsonl,
         timeline-events.jsonl
       manifests/<run-timestamp>.json        # rate-limit usage, counts, commit
     SHA

     JSONL is later loaded into MySQL with a small bulk-insert step once the
     schema
     is finalized. Skip SQLite/SQLDelight — adds schema-migration burden with no
     queryability gain at this volume.

     Module layout

     :utils (domain-agnostic, package dev.cse3000.gh)

     - client/GithubClient.kt — Ktor wrapper. Suspend functions per endpoint:
     listPullRequests, getPullRequest, listIssueComments, listReviewComments,
     listReviews, listReactions, listTimelineEvents, listChecks, getContent,
     runGraphQL. Uses ktor-client-cio + content-negotiation + kotlinx-json.
     - client/RateLimiter.kt — Semaphore(8) for concurrency cap + adaptive
     throttle
     reading X-RateLimit-Remaining / X-RateLimit-Reset; suspends until reset
     when remaining drops below a configurable floor (default 100).
     - client/RetryPolicy.kt — handles 403 + Retry-After (secondary rate limit)
     and 5xx with exponential backoff; treats 304 Not Modified as a cache hit.
     - client/Paginator.kt — Flow<JsonElement> over Link header pagination.
     - cache/EtagStore.kt — load/save etags.json, attach If-None-Match per URL.
     - cache/RawCache.kt — write/read JSON keyed by URL → file path.
     - cache/SyncCursor.kt — load/save last-sync.json per endpoint key.
     - io/JsonlWriter.kt — append-only JSONL output.
     - io/Env.kt — read GITHUB_TOKEN (fail fast if missing).
     - io/RunManifest.kt — emit run-summary JSON at end of each scrape.
     - model/ — generic GitHub DTOs (GhUser, GhIssue, GhPullRequest,
     GhComment, GhReview, GhReaction, GhLabel, GhTimelineEvent,
     GhCheckRun, GhDiscussion, GhDiscussionComment, RateLimitInfo).
     These map directly to GitHub responses and are shared by both scrapers.
     - scraper/ProposalScraper.kt — interface: suspend fun run(); fun 
     discover(): Flow<ProposalRef>.

     :utils/build.gradle.kts already has the kotlinx bundle. Add Ktor + plugin:
     alias(libs.plugins.kotlinPluginSerialization) and Ktor dependencies.

     :keep (package dev.cse3000.keep)

     - model/KeepProposal.kt, model/KeepProposalRef.kt, model/KeepDiscussion.kt
     - scrape/KeepProposalDiscovery.kt — list PRs that touch proposals/*.md;
     resolve linked issue via the PR's "closing issues" GraphQL field with REST
     body-parse fallback (Fixes #N).
     - scrape/KeepDiscussionsDiscovery.kt — GraphQL query
     repository(owner:"Kotlin", name:"KEEP") { discussions(first:100, 
     after:$cursor) { ... } } to enumerate discussions, then fetch comments +
     replies + reactions.
     - scrape/KeepScraper.kt — orchestrator wired into Main.kt CLI.
     - Main.kt — CLI entry (Gradle application plugin). Subcommands full and

     Addendum: wire up periodic flushing + use kotlin.time.Duration everywhere

     Context

     Two related cleanups:

     1. JsonlWriter#flush was added speculatively during implementation but
     never
     called. For a multi-hour scrape that gets Ctrl-C'd (or hits kill -9),
     several minutes of buffered JSONL lines and the latest ETag/cursor state
     can currently be lost. We want to flush all in-flight state to disk every
     60s so a kill loses at most ~60s of progress.
     2. Time values in the codebase are a mix: some sites use raw Long
     milliseconds (retryDelayMs(): Long, delay(60_000)), some have been
     linter-touched into (...).milliseconds. Standardize on
     kotlin.time.Duration everywhere a time value is constructed, returned,
     stored, or passed across a function boundary — only convert to/from
     primitive seconds/ms at the I/O edge (HTTP header parsing, epoch math).

     Approach — periodic flush

     A periodic-flush coroutine launched from each Main.kt. It persists the ETag
     store, sync cursor, and all open JSONL writers on a fixed cadence, then is
     explicitly cancelled in the finally block before the run manifest is
     written.

     The flush body itself runs under withContext(NonCancellable) so
     cancellation
     during the actual disk write doesn't leave the ETag/cursor JSON files in a
     partially-written state (atomic-rename in EtagStore.persist /
     SyncCursor.persist already handles process-kill mid-write, but
     NonCancellable keeps the cooperative-cancellation path clean).

     Approach — Duration policy

     - Function signatures that represent a time value take/return
     kotlin.time.Duration, never Long ms or Long sec.
     - Constants are constructed via the extension properties:
     60.seconds, 30.seconds, 500.milliseconds, etc. — not
     60_000.milliseconds or (60 * 1000).milliseconds.
     - HTTP header values (Retry-After, X-RateLimit-Reset) are parsed as
     Long (their wire format) and immediately wrapped: headerSec.seconds.
     - Epoch arithmetic (System.currentTimeMillis() / 1000 vs an epoch
     reset stamp) stays in Long; only the resulting delta is converted to
     Duration before being returned to a caller or passed to delay.
     - delay(Duration) is preferred over delay(Long) so cancellation behavior
     and units are unambiguous at the call site.

     Addendum: replace "∞" denominators with discovered totals

     Context

     Progress logs in IssueAndPrCollector and KeepDiscussionsCollector currently
     display processed/limit ?: "∞", which shows 25/∞ on a full scrape because
     the total isn't known. We want a real denominator so the user can estimate
     how long a run will take and what fraction of the work is done.

     Approach

     Three sources, three different mechanisms — pick whichever is cheapest per
     endpoint:

     1. REST list endpoints (/repos/{slug}/issues, /repos/{slug}/pulls):
     GitHub returns a Link: <...&page=N>; rel="last" header on the first
     paginated response. Probing with ?per_page=1 makes N exactly equal to
     the total item count. Costs 1 extra request per phase per run; subsequent
     runs serve the probe from ETag cache (304, no quota cost).
     2. GraphQL discussions connection: has a built-in totalCount field —
     free, just an extra leaf on the existing query.
     3. KEP yaml discovery: total is already known in-memory after the tree
     filter (kepYamlEntries.size), already logged correctly. No change.

     Caveat for /pulls in incremental mode

     The /repos/{slug}/pulls endpoint does not support a since query
     parameter, so the probe returns all-time PR count regardless of cursor. The
     collector then client-side filters out PRs older than sinceCursor. The
     honest log message in that case is "of N total in repo" so it's clear the
     denominator is pre-filter.

     /issues does honor since, so the probe gives the post-filter total
     directly — the denominator is meaningful.

     Denominator policy in the progress log

     denominator = limit ?: total ?: "?"

     i.e. respect --limit if set; otherwise show the discovered total; otherwise
     fall back to "?" only if the probe genuinely failed (no Link header).

     Addendum: graceful cancellation of the scraping Gradle tasks

     Context

     Today, hitting Ctrl-C during ./gradlew :keep:run (or the aggregator
     fullScrape / updateScrapedData tasks) causes the JVM to exit before the
     finally blocks finish: the run manifest never gets written, ctx.persist()
     in the success path is skipped, and the JSONL writers may have buffered
     bytes that are lost. The only thing currently saving us is the 60s periodic
     flush — anything emitted in the last 0–60s of the run is lost on a kill.

     We want Ctrl-C (and any other JVM shutdown signal) to:

     1. Stop launching new HTTP / git work,
     2. Let in-flight per-item work complete or unwind cleanly,
     3. Persist etags, cursor, gitCursor, and JsonlSink to disk,
     4. Write a run manifest reflecting that the run was cancelled, and
     5. Exit non-zero (or zero, as long as the manifest is on disk).

     A bounded shutdown timeout (default 30s) keeps a stuck network call from
     preventing exit forever — a second Ctrl-C still hard-kills.

     Approach

     JVM shutdown hook + cooperative coroutine cancellation, leveraging the
     structure already in place:

     1. The two Main.kt files already wrap everything in runBlocking { ... }
     with a try/catch/finally + a flushJob child coroutine. The root
     runBlocking job already covers all collectors via structured concurrency.
     2. Register a JVM shutdown hook that:
       - Calls rootJob.cancel(CancellationException("Shutdown signal 
     received")),
       - Then runBlocking { withTimeoutOrNull(30.seconds) { rootJob.join() } }
     so the hook thread blocks until cleanup completes (or the timeout fires).
     3. The existing finally block is the cleanup path. It must work under
     cancellation, so:
       - All suspending cleanup (ctx.persist(), flushJob.join(), manifest
     write) is wrapped in withContext(NonCancellable) { ... }.
       - The finally also removes the shutdown hook (so a normal-exit path
     doesn't leave a dangling hook).
     4. Catch CancellationException in main's try/catch to set a cancelled
     flag; do NOT rethrow it (we want main to exit cleanly with a written
     manifest, not propagate a stack trace). Other exceptions are still
     rethrown.
     5. Two small atomicity tweaks elsewhere so cancellation can't leave
     half-written state on disk:
       - JsonlWriter.append: build line + lineSeparator() once and do a
     single writer.write(...) call inside the mutex. Removes the
     write-then-newLine race where cancellation between the two calls
     produces a JSONL line with no newline.
       - GithubClient.fetchWithRetry's 200-success branch: wrap
     cache.put(url, text) + etags.put(url, etag) in
     withContext(NonCancellable) so an ETag is never recorded for a body
     that didn't make it to the cache (would cause a future 304 with no
     cached body — already an error() in the 304 branch).

     Critical files to be modified

     - utils/src/main/kotlin/dev/cse3000/gh/io/RunManifest.kt
       - Add val cancelled: Boolean = false to the RunManifest data class
     (with @SerialName("cancelled") for consistency).
     - utils/src/main/kotlin/dev/cse3000/gh/io/JsonlWriter.kt
       - Replace the writer.write(line); writer.newLine() pair with a single
     writer.write(line + System.lineSeparator()) so the on-disk state is
     always a complete line or no line at all.
     - utils/src/main/kotlin/dev/cse3000/gh/client/GithubClient.kt
       - Wrap the cache-put + etag-put pair in the 2xx branch in
     withContext(NonCancellable) { ... }. Add import 
     kotlinx.coroutines.NonCancellable
     and import kotlinx.coroutines.withContext (already imported via wildcard).
     - keep/src/main/kotlin/dev/cse3000/keep/Main.kt and
     kep/src/main/kotlin/dev/cse3000/kep/Main.kt
       - Capture val rootJob = coroutineContext.job at the top of runBlocking.
       - Build a JVM shutdown hook (see snippet below) and register it via
     Runtime.getRuntime().addShutdownHook(...).
       - Add var cancelled = false and a dedicated catch (ce: 
     CancellationException)
     branch that sets cancelled = true, logs at WARN, and falls through (no
     rethrow).
       - In the finally, wrap flushJob.join() + ctx.persist() + manifest write
           - ctx.close() in withContext(NonCancellable) { ... }.
       - Pass cancelled = cancelled into the RunManifest(...) constructor.
       - At the end of finally, runCatching { 
     Runtime.getRuntime().removeShutdownHook(hook) }
     so a normal exit doesn't leave the hook dangling.
       - Define private val SHUTDOWN_TIMEOUT = 30.seconds near the top of the
     file (or pull into a shared :utils constant — duplication of one line
     is fine for now).

     Hook shape (same in both Main.kt files):
     val rootJob = coroutineContext.job
     val shutdownHook = Thread {
         log.warn("Shutdown signal received; cancelling scrape gracefully (up to
      {})", SHUTDOWN_TIMEOUT)
         rootJob.cancel(CancellationException("Shutdown signal received"))
         runBlocking {
             val finished = withTimeoutOrNull(SHUTDOWN_TIMEOUT) { rootJob.join()
      }
             if (finished == null) log.warn("Graceful shutdown timed out after
     {}", SHUTDOWN_TIMEOUT)
         }
     }
     Runtime.getRuntime().addShutdownHook(shutdownHook)

     Why this works under Gradle's JavaExec

     The application plugin's run task forks a separate JVM for the scraper.
     Whether the user Ctrl-Cs the gradle wrapper, kills the gradle daemon, or
     Gradle terminates the JavaExec process on its own, the child JVM ultimately
     receives a shutdown signal — at which point our hook fires. Hooks run on
     fresh threads, so they can outlive the main thread's runBlocking long
     enough to drive cleanup.

     Addendum: fix countListEndpoint fallback when GitHub omits rel="last"

     Context

     The probe in GithubClient.countListEndpoint reads the Link header to
     discover the total item count of a list endpoint (e.g. /issues?since=...).
     GitHub does not always include rel="last" — for /issues requests with
     the since query param specifically (and a handful of other filtered
     endpoints), GitHub returns only rel="next" for paginated multi-page
     responses.

     The current fallback when lastPageNumber returns null is the response
     body's array size. With per_page=1, that's always 1 — which is reported
     as the total. So in incremental (update) mode where since is set, every
     issues phase logs Issues progress: N/1 processed regardless of how many
     issues actually need fetching. Misleading.

     Approach

     Distinguish the two cases that produce a missing rel="last":

     1. Single-page result — there are 0 or 1 pages of results, no rel="next"
     either. The body's array size IS the true total. Return it.
     2. Multi-page result with last omitted — rel="next" is present even
     though last isn't. The total is genuinely unknown via this probe.
     Return null so the denominator in the log shows ?, which is honest,
     instead of a wrong 1.

     Paginator.nextLink(...) already exists and returns the rel="next" URL
     when present — reuse it.

     Critical files to be modified

     - utils/src/main/kotlin/dev/cse3000/gh/client/GithubClient.kt
       - In countListEndpoint, replace the single-line Elvis fallback:
     Paginator.lastPageNumber(resp.headers[HttpHeaders.Link])
         ?: (Jsons.compact.parseToJsonElement(resp.bodyAsText()) as?
     JsonArray)?.size
       - with explicit branching:
     val link = resp.headers[HttpHeaders.Link]
     Paginator.lastPageNumber(link)?.let { return@withPermit it }
     if (Paginator.nextLink(link) != null) return@withPermit null
     return@withPermit (Jsons.compact.parseToJsonElement(resp.bodyAsText()) as?
     JsonArray)?.size

     No other files change. The downstream callers in IssueAndPrCollector
     already treat null as "?" via denominator = limit ?: total ?: "?".

     The sibling repo is treated as an external dependency — both the
     producer (:loader) and consumer (:rq3) reference it by filesystem path

     manage their sibling-repo checkout with normal git pull / git push; no
     gitlab credentials live inside this build.

     Sibling repo expectations (proposals-db)

     We don't own this repo, but the contract it must provide is:

     - schema/init.sql — collaborative DDL. All tables include a source column
     (or analogous discriminator) so each contributor's data can be deleted +
     re-inserted independently.
     - proposals.db — committed SQLite file, kept current with schema/init.sql.
     - scripts/init-db.sh — drops proposals.db and rebuilds it from scratch
     via schema/init.sql. Used when the schema changes incompatibly.
     - README.md — documents the contributor workflow (apply your inserts →
     commit
     → push) and reminds contributors to coordinate to avoid concurrent .db
     merge
     conflicts.

     This addendum doesn't need to build the sibling repo for them — it just
     specifies the contract :loader writes against and :rq3 reads from.

     :loader module (NEW)

     Goal: convert this scraper's normalized JSONL streams into a single SQL
     file that, when applied once to the shared proposals.db, populates two
     project IDs' worth of rows (one for KEEP, one for KEP).

     This is a one-shot push — no incremental updates. After this contributor
     applies their data.sql once, they're done. If a re-apply is ever needed
     (e.g., schema rebuild), the maintainer rebuilds proposals.db from
     db-schema.txt and every contributor re-applies their one-shot output.

     :loader
       src/main/kotlin/dev/cse3000/loader/
         SchemaModel.kt           # Kotlin types mirroring db-schema.txt
     (manually kept in sync)
         JsonlSource.kt           # streams from data/normalized/<stream>.jsonl
         IdAllocator.kt           # sequential ID generator within a
     contributor-assigned range
                                  # (e.g. for keepProjectId=3, person_ids start
     at 3_000_000)
         KeepMapper.kt            # JSONL streams (keep-*) → SchemaModel rows
     for the KEEP project_id
         KepMapper.kt             # JSONL streams (kep-*)  → SchemaModel rows
     for the KEP project_id
         SqlWriter.kt             # emits INSERT statements with sqlite-safe
     quoting
         Main.kt                  # CLI entry
       build.gradle.kts           # apply application plugin; depends on
     :scraper

     No PersonResolver, no -PsharedDb read. Person dedup is deferred to
     :rq3 post-processing. The loader simply allocates person_id values in
     a contributor-specific range so they don't collide with other contributors'
     allocations. :rq3 (or whatever consumer cares) can dedupe by
     (PersonUsername.domain, PersonUsername.username) later, merging duplicate
     Persons into one canonical row and updating FKs.

     ID allocation strategy: a small range per project keeps things simple.
     Convention: person_id ∈ [projectId × 1_000_000, (projectId+1) × 1_000_000).
     For a contributor with two project IDs (3 and 4), use the smaller as the
     base (person_id starts at 3_000_000). Same scheme for organisation_id
     and comment_id. With 10 projects total and at most ~tens of thousands of
     distinct authors per project, 1M slots is plenty of headroom.

     Push workflow (manual, one-shot)

     # 1. Scrape (run scrapers to completion at least once)
     ./gradlew :keep:run --args="--mode=full"
     ./gradlew :kep:run  --args="--mode=full"

     # 2. Generate the one-shot SQL using assigned project ids
     ./gradlew :loader:run -PkeepProjectId=3 -PkepProjectId=4

     # 3. Pull the sibling repo and apply
     cd ~/projects/proposals-db && git pull
     bash ~/projects/this-repo/loader/build/export/keep-kep/apply.sh
     ./proposals.db

     # 4. Commit + push the modified .db
     git add proposals.db
     git commit -m "[keep-kep] one-shot import"
     git push

     Because the loader doesn't read the existing proposals.db, steps 2 and
     3 don't have to be tightly coupled — there's no race window. Other
     contributors can have pushed between your scrape and your apply. The only
     requirement is that the schema in the .db at apply time matches the schema
     the loader was written against (compare
     loader/build/export/keep-kep/schema.txt
     against the .db's sqlite_schema if in doubt).

     The apply.sh is regenerated under loader/build/... (a build-output path,
     gitignored in this repo) on every loader run.

     cd ~/projects/proposals-db && git pull

     Operational notes

     - Concurrent commits to proposals.db will conflict (binary, no merge).
     Treat the sibling repo as a serialized resource — coordinate via Slack /
     whatever channel before pushing. Since the loader doesn't read the .db,
     there's no race window inside this contributor's flow; only the
     git push of the modified .db needs serialization across contributors.
     - Schema changes: db-schema.txt is coordinated separately. If it
     changes, every contributor updates their SchemaModel.kt, re-runs
     :loader:run, the sibling-repo maintainer rebuilds an empty proposals.db
     from the new schema, and each contributor re-applies their one-shot
     output once. After that round-robin, the .db is the new canonical state.
     - No idempotency-on-re-apply guarantee: re-running apply.sh against
     a .db that already contains this contributor's rows will fail on PRIMARY
     KEY violations (Proposal, ProposalRevision, etc.). That's intentional —
     this is a one-shot push. If a re-apply is genuinely needed, the
     contributor manually deletes their project_id rows first, or the
     maintainer rebuilds the .db from scratch.
     - Person ID range collision avoidance: each contributor's IdAllocator
     uses [smallestAssignedProjectId × 1_000_000, +1_000_000) for person_id,
     organisation_id, and comment_id allocations. With 10 projects and
     ~10⁶ slots per range, this is collision-free without coordination. If a
     contributor genuinely produces more than 1M Persons (unlikely), bump the
     multiplier to 10M.
     - Person dedup is not the loader's job. The same GitHub user appearing
     in two contributors' data will exist as two Person rows with different
     IDs after both contributors apply. :rq3 (or a future maintenance task)
     can dedupe by (PersonUsername.domain, PersonUsername.username) once
     all data is in. Flag to schema collaborators: add a UNIQUE(domain, 
     username) index to PersonUsername to make dedup-via-MERGE-and-FK-rewrite
     straightforward downstream.

     1. ./gradlew :loader:build — module compiles cleanly.
     2. Synthetic push test: with a populated data/normalized/, run
     ./gradlew :loader:run -PkeepProjectId=3 -PkepProjectId=4. Confirm
     loader/build/export/keep-kep/ contains schema.txt, data.sql,
     apply.sh, apply.bat. Spot-check data.sql: project_id is 3 or 4
     on every project-scoped row; person_id values are all in

     sane (Persons declared before their first reference).
     3. End-to-end apply: in a tmp dir,
     sqlite3 tmp.db < db-schema.txt && bash apply.sh tmp.db. Then

     for project_id=4 vs distinct proposals in kep-yaml-revisions.jsonl.
     SELECT COUNT(*) FROM Comment WHERE project_id IN (3,4) matches the
     sum of the relevant comment streams.
     4. Cross-contributor coexistence: simulate another contributor by

     Addendum: scrape GitHub user metadata for a manually-supplied login list

     Context

     The loader maps GitHub commenters / authors / committers into Person /
     PersonUsername rows (via the personByGHLogin map inside KeepMapper /
     KepMapper). Those rows currently carry only the login — no display name,
     no organisation, no profile blob. We want a separate one-off scrape step
     that
     takes a list of GitHub logins and fetches each user's full metadata via
     GET /users/{login}, emitting it as JSONL for later enrichment.

     User constraint: don't over-automate this. The list of logins is supplied
     manually (a plain text file). The fetch task is invoked manually, once. No
     auto-discovery from the loader, no auto-enrichment of the shared SQLite.
     The
     researcher decides what to do with users.jsonl afterwards (extend the
     loader to read it back and fill Person.full_name, push to a separate file
     for :rq3 post-processing, whatever).

     Approach

     A new standalone scrape entry point in :scraper that reuses every piece of
     existing infrastructure (GithubClient for ETag/rate-limit/retry/IOException
     handling, runScrape for shutdown hook + flush + manifest). The collector
     itself is ~30 lines because GitHub's /users/{login} endpoint needs no
     pagination — one request per login, one row out.

     $env:GITHUB_TOKEN = "ghp_..."
     ./gradlew :scraper:runUsers -Pinput=path/to/logins.txt

     Input file format: one GitHub login per line, blank lines and lines
     starting
     with # ignored. Example:

     # generated by hand from PersonUsername rows
     JakeWharton
     chrisbanes
     elizarov

     Output: <dataDir>/normalized/users.jsonl — one line per successfully
     fetched
     user, each row is the raw /users/{login} response (login, id, name,
     company,
     location, email-if-public, bio, blog, twitter_username, public_repos,
     followers, following, created_at, updated_at, etc.) with the standard
     _scraped_at / _repo (set to literal "users") meta fields the rest of
     the scraper adds.

     Default dataDir for this task is data/users/ so the user-fetch state
     (ETag store, raw cache, manifest) is isolated from your main KEEP/KEP
     scrape
     caches and can be deleted independently if you want a fresh run.

     Critical files to be created / modified

     - scraper/src/main/kotlin/dev/cse3000/gh/scraper/UsersCollector.kt (NEW)
       - Constructor: (client, sink, owner = "users", repo = "users", repoTag = 
     "users") — owner/repo are placeholders for the meta fields; the API path is
      fixed as /users/{login}.
       - suspend fun fetch(login: String): hits client.getJson("/users/$login"),
      emits to users.jsonl with mapOf("login" to login) meta. Catches "404 Not
     Found" thrown by fetchWithRetry and logs a WARN; doesn't abort the whole
     batch.
       - suspend fun run(logins: List<String>, limit: Int? = null): iterates
     with progress logging every 25; respects optional limit for smoke tests.
     - scraper/src/main/kotlin/dev/cse3000/gh/cli/UsersMain.kt (NEW)
       - Reads --input=path (required) and --dataDir=path (default data/users)
     from system properties (forwarded by the Gradle task from -P).
       - Parses the input file: filter blanks + # lines, trim, dedupe, sort.
       - Wraps the collector call in runScrape(...) for the standard scaffolding
      (shutdown hook, periodic flush, manifest, stop-file watcher). The body
     block constructs UsersCollector(...) and calls run(logins, limit). Repo
     slug in the manifest can be "github-users" to keep manifests distinct from
     regular scrape runs.
       - Reuses parseScrapeArgs(args, "scraper-users", allowProposals = false)
     to share the --limit / --mode flag parsing — --mode=full|update here just
     toggles whether ETag-cached 304s are honored, so update is the sane default
      for re-runs.
     - scraper/build.gradle.kts (EDIT)
       - Add a runUsers JavaExec task with mainClass = 
     "dev.cse3000.gh.cli.UsersMainKt".
       - Forward input and dataDir Gradle properties as system properties (same
     pattern the existing :loader:run config uses).
     - README.md (EDIT)
       - Add a short "Scraping user metadata" subsection under "Running the
     scrapers" pointing at :scraper:runUsers with the input-file format, a
     one-line example, and a note that the file is supplied manually (the loader
      can optionally drop one alongside data.sql if the researcher wants to wire
      that up — single line in SqlWriter).

     Why a new task and not a --include=users phase

     The other phases are repo-scoped: they all hit /repos/{slug}/... endpoints
     and slot into the existing IssueAndPrCollector / DiscussionsCollector /
     CommitsCollector shape. User metadata is identity-scoped (/users/{login})
     and the input is a manually-curated list, not a repo. Folding it into the
     phase enum would muddy ScrapePhase (most phases require --repo=; this one
     doesn't). A dedicated runnable task keeps the surface clean.

     What's intentionally NOT done

     - No automatic discovery of logins from the loader's output. The loader can
     emit logins.txt if you add one line to SqlWriter (write distinct
     PersonUsername.username values where domain == "github.com"), but
     that's optional and out of scope for this addendum.
     - No automatic enrichment of proposals.db Person rows. The output is raw
     JSONL; downstream (a :rq3 analysis step or a future loader extension)
     decides if/how to merge.
     - No GraphQL bulk lookup. GitHub's node(id: "MDQ6VXNlcjE=") would batch
     ~100 users per query and save quota, but for ~hundreds-to-low-thousands of
     users it's not worth the codegen complexity. REST /users/{login} is
     one request each, ETag-cached on rerun.

     Verification

     1. ./gradlew :scraper:build — green.
     2. Smoke test: write tmp/logins.txt with 3 known logins (e.g.,
     JakeWharton, elizarov, nonexistent-login-9999999).
     ./gradlew :scraper:runUsers -Pinput=tmp/logins.txt -PdataDir=tmp/users.
     Expect: tmp/users/normalized/users.jsonl has 2 rows; the 404 login
     logs a single WARN and is skipped; manifest at
     tmp/users/manifests/github-users-update-*.json reports requests_made=3,
     errors=[] (the 404 is handled, not fatal).
     3. Re-run: same command. Manifest reports requests_304=2 and zero
     new normalized rows (the third login still 404s and is skipped quickly).
     4. Cancel test: feed a long list (e.g., 500 logins), run, hit Ctrl-C
     (or touch tmp/users/STOP). Manifest has cancelled=true; users.jsonl
     has the partial set of rows fully formed (no truncated lines), and the
     ETag cache is populated for the logins that were fetched before
     cancellation.

     Addendum: nest this repo inside a GitLab "monorepo" via git submodules

     Context

     This whole project moves into a GitLab "monorepo" — but a
     git-submodule-based
     one rather than a single flattened repo. Each contributor's project remains
     its own standalone GitLab repository with its own history; the monorepo
     root
     is a separate GitLab project that wires every contributor in as a submodule
     and additionally holds the shared artifacts (db-schema.sql and, depending
     on team decision, proposals.db).

     This contributor's repo keeps its current name —
     CSE3000_RQ3-KEEP-KEP (matching rootProject.name in
     settings.gradle.kts) — and lives as a submodule directory of the same name
     inside the monorepo root.

     Layout after the move:

     <monorepo-root>/                       # standalone GitLab project, its own
      .git
       .gitmodules                          # registers every contributor
     submodule
       db-schema.sql                        # shared, tracked by the monorepo
     .git
       proposals.db                         # shared SQLite (committed binary,
                                            #   tracked by the monorepo .git;
                                            #   optional — see "Open items")
       CSE3000_RQ3-KEEP-KEP/                # this repo, as a submodule (own
     .git)
         settings.gradle.kts                # rootProject.name unchanged
         keep/  kep/  scraper/  loader/  rq3/
         data/  build/  ...
       <other-contributor-A>/                # submodule
       <other-contributor-B>/                # submodule
       ...

     Three goals to satisfy at once:

     1. Migrate without disruption — current Gradle commands (./gradlew 
     :keep:run,
     :loader:run, :rq3:syncSharedDb, etc.) keep working from inside
     CSE3000_RQ3-KEEP-KEP/ with the same arguments. Existing repository
     history is preserved (submodules don't rewrite history).
     2. Open just this folder in IntelliJ — sibling contributor folders aren't
     indexed, their Gradle modules don't show up, our :run configurations
     stay clean. The submodule model makes this even cleaner: a contributor
     can clone just their own repo and never touch the monorepo root, and
     they can still clone the monorepo with --recurse-submodules when they
     want the whole picture.
     3. Read/write the parent on demand — read the shared db-schema.sql
     (loader needs the snapshot); write the shared proposals.db (apply our
     data.sql). All other parent-dir touches happen via plain shell + git
     commands at the monorepo-root level.

     Recommended approach

     Keep CSE3000_RQ3-KEEP-KEP/ as its own self-contained Gradle build — its
     own settings.gradle.kts, its own wrapper, its own rootProject.projectDir,
     its own GitLab project, its own .git/. The monorepo root is not a
     Gradle build; it's a directory of git submodules plus a few shared files.
     This
     is the simplest possible model and the one that makes "open just this
     folder"
     trivial in any IDE: IntelliJ opens CSE3000_RQ3-KEEP-KEP/, sees
     settings.gradle.kts there, treats that as the project root, and never
     touches sibling submodules. The git VCS root IntelliJ detects is this
     submodule's .git/, not the monorepo root's — so the IDE's "Changes" view
     shows only this contributor's diffs, and commits go to this repo's history.

     The few places that point outside this folder (the schema snapshot, the
     shared-DB sync target) are already parameterized via -P… properties or env
     vars. We add a single new convention — a monorepoRoot Gradle property,
     default
     .. — and route all outward-facing default paths through it. That way the
     defaults "just work" inside the monorepo, and a standalone clone outside
     the
     monorepo overrides one property and is back to the current behavior.

     Why submodules instead of a flattened monorepo?

     A flattened monorepo (one giant .git/ covering everyone) would force every
     contributor's IDE to walk the whole tree on git operations and would mix
     unrelated commit histories into one log. Submodules keep each contributor's
     repo independent — independent push/pull, independent issues/MRs on GitLab,
     independent visibility — while still letting the monorepo root pin a
     coherent
     "snapshot of the whole project" via the recorded submodule SHAs.

     Why not a Gradle composite build at the monorepo root?

     includeBuild from a monorepo-root settings.gradle.kts would let you run
     ./gradlew :CSE3000_RQ3-KEEP-KEP:keep:run from the monorepo root, but it has
     real costs:

     - IntelliJ pointed at the monorepo root would index every contributor's
     source — the exact "open just this folder" property we want to keep.
     - Gradle daemons get bigger; config-cache invalidation across contributors
     is
     a footgun.
     - Cross-contributor dependencies aren't a use case here — each scraper is
     independent.

     Skip composite. Each contributor submodule is its own standalone Gradle
     build.

     Why not move the IntelliJ project root up?

     If you opened the monorepo root in IntelliJ, every contributor's submodule
     would get auto-imported (or at minimum land in scope-search), and our
     finely-tuned :run configurations would coexist with sibling contributors'
     configs. Keep IntelliJ pointed at CSE3000_RQ3-KEEP-KEP/.

     Why not hard-code ../db-schema.sql?

     Two reasons. One, contributors who clone just this repo (the submodule, by
     itself) would break. Two, the lookup chain is already the shape we want
     (parameterized + ordered fallbacks) — adding the monorepo root path is one
     more entry in a list that already exists.
